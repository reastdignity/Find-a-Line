# Find-a-Line

Finds possible highlines in elevation data: anchors on steep pixels, every pair checked for clearance under the webbing, results shown on an interactive Leaflet map. User-facing docs: [README.md](README.md) (reference), [setup-for-regular-folk.md](setup-for-regular-folk.md) (step-by-step guide) and [docs/deployment.md](docs/deployment.md) (the public site on a VPS with Ubuntu 26.04, nginx, certbot and fail2ban on the host: SSH, firewall, OAuth, backups, checks; keep it in step with `deploy/` (`deploy/vps.sh` runs its commands), compose.yaml and `tests/nginx_check.sh`). Plans, decisions already made, their order and open checks: [docs/roadmap.md](docs/roadmap.md); read it before proposing a design.

## Run it
- Python 3.12+ (scipy 1.18 needs it). Dependencies in `pyproject.toml`, pinned in `uv.lock` (`uv sync`, `uv run findaline.py ...`; the user's `.venv` is git-ignored). For a session environment outside the repo: `UV_PROJECT_ENVIRONMENT=<dir> uv sync --frozen` (uv itself can be pip-installed into any venv: `python -m uv`). After changing dependencies run `uv lock` and the full regression set.
- Tests: `pytest` (offline, ~30 s: synthetic canyon + Żabi Koń clip in `tests/data`, units, the viewer against Python, the web app) and `python tests/regression.py` (real searches, see docs/regression-tests.md). `tests/test_viewer.py` is skipped without Node and `npm install` in `viewer/`.
- CI: `.github/workflows/ci.yml` (GitHub Actions: `pytest` on Linux and Windows, `pip-audit` and `npm audit`, and `docker`: the image built, a search and both services run in it, `docker compose config`, the source address of the published port, nginx and fail2ban through `tests/nginx_check.sh`); keep its steps in line with these commands.
- Docker (the public site): `Dockerfile` (uv build stage, python-slim runtime without uv, uid 10001; base images pinned by digest, how to update them is in its header) and `compose.yaml` (`web --public` and `worker --public`, one data volume at `/data`, read-only root, `/tmp` tmpfs, settings in `findaline.env`, secrets in `secrets/`, resources in `.env`). Docker Desktop is installed on the dev PC but not on PATH (`export PATH="/c/Users/Krzysiek/AppData/Local/Programs/DockerDesktop/resources/bin:$PATH"` in Git Bash); test stacks get their own project name (`docker compose -p <name>`), settings and dummy secrets outside the repo (`--project-directory <scratch>` with an override setting `build.context` to the checkout), and are removed afterwards (`down -v`). A missing system library shows only at run time: after changing dependencies or the base image, `ldd` every `.so` of the venv in the image (numba's optional `omppool`/`tbbpool` may stay unresolved). `web` publishes `127.0.0.1:${WEB_PORT:-8765}` only (test stacks: another `WEB_PORT`, 8765 is often the user's local app); the app trusts `X-Forwarded-For` from the gateway of its network `web` (`172.30.0.1`, fixed in compose.yaml: connections to a published port arrive from it). `tests/nginx_check.sh` installs `deploy/nginx` and `deploy/fail2ban` with the functions of `deploy/vps.sh` (sourced: `nginx_files`, `fail2ban_files`, also `ufw_files` on ufw's stock rules) on Ubuntu 26.04's packages and checks nginx in front of the running web service (`docker run --rm --network <project>_web -v <checkout>:/src:ro ubuntu:26.04@<digest of ci.yml> bash /src/tests/nginx_check.sh`; Ubuntu's `nginx.conf` already sets `server_tokens`, `ssl_protocols` and `gzip` in its `http` block: such directives go per server, never into `conf.d/`). Anything written at run time must go to the data folder or `/tmp` (`HOME`, `NUMBA_CACHE_DIR`, `MPLCONFIGDIR` point into `/data/home`); a file the image needs at run time must not be excluded by `.dockerignore` (it keeps only the scripts and `viewer/dist`).
- Before adding a dependency, check the current docs of the version that gets installed (Starlette 1.x: no `add_event_handler`, use `lifespan`; its TestClient wants `httpx2`, not `httpx`) and run the tests with deprecation warnings visible.
- `python findaline.py --lat 50.1559508 --lon 19.7562722` (Żabi Koń, Poland). `--help` lists everything. Other commands (first argument): `cache status|update`, `osm download|update` (update.py), `web` (web.py; runs the worker in-process unless `--no-worker`), `worker` (jobs.py: the worker as its own process).
- `python findaline.py web --no-browser --port 8799 --data-dir <scratch>` runs the web app for tests (start it in the background). Headless Edge waits for the open event stream: stub `EventSource` in a test page (see docs/regression-tests.md) or use `--timeout` for screenshots.
- `web --public` / `worker --public`: the public site behind a reverse proxy (`settings.PublicSettings`: `FINDALINE_PUBLIC_URL`, `FINDALINE_TRUSTED_PROXY`, `FINDALINE_CONTACT`, also from Docker secrets in `/run/secrets`); refuses to start without them; `web --public` also needs `settings.AccountSettings` (`FINDALINE_SESSION_SECRET`, at least 32 characters; `FINDALINE_GITHUB_CLIENT_ID`/`_SECRET` and/or `FINDALINE_GOOGLE_CLIENT_ID`/`_SECRET`, a provider without both is not offered; `FINDALINE_ADMINS` as `github:<numeric id>,google:<sub>`; `FINDALINE_SIGNUP=approval|open|closed`); `web --public` never runs the worker, and `--host` other than loopback needs `--public`. Tests: `PublicSettings(public_url="http://localhost:<port>", ...)` and a `TestClient` with that `base_url` (`tests/test_public.py`); sign-in against fake providers: `FakeProviders` there (an `httpx2.MockTransport` passed as `create_app(oauth_transport=...)`, which Authlib's clients take through `client_kwargs`), `sign_in(client, providers, user)`.
- `--no-plot` is required when running without a desktop session (the matplotlib window blocks). `--yes` skips the confirmation questions; without a terminal they default to "no".
- Long runs: start them in the background and wait for the notification. Each search has its own `work/<id>/` (a web job `work/jobs/<job>/<phase>`, removed when the job ends or is killed) and downloads write unique `.part` files (the worker deletes those older than a day), so searches may overlap, but tests run one after another (each search uses all cores).
- Data folder (`--data-dir`, `FINDALINE_DATA`, default the repo): `cache/`, `runs/`, `work/`; layout and index in `cache.py`. A cache without the current `cache/LAYOUT` is refused (decided for the cache layout: no migration code, the user moves or deletes the folders by hand).
- Without a terminal, progress is printed as `[Download] ...` / `[Compute] ...` lines every 10 s; `FINDALINE_PROGRESS=bars|text` forces a mode.

## Things that must stay in sync
- `mapping.group_lines` (Python) and `groupLines` (`viewer/src/grouping.ts`): the same greedy algorithm with the same cell index and the same order of the lines (`_rank` / `compare`: clearance, longest, height); the browser must produce the same groups. Values used for grouping are passed to the viewer unrounded. The viewer may show another line of a group than its representative (chosen by the user: `chosen` in `main.tsx`, keys from `keys.ts`), but never changes the members of a group.
- `sag.py` and `viewer/src/sag.ts`: the same solver; results match to 1e-6 m. `tests/test_viewer.py` checks both pairs with Node, and that `viewer/dist` is built from `viewer/src`.
- `linesearch.covered_metres` (metres over water/filled gaps of every line, numba) and `helpers.line_profile` (`water_m`, `filled_m`): the same pixels and formula; `tests/test_units.py` compares them. Areas compute profiles only for the lines shown for groups (`search._lines`), circles for all.
- The run data written by `mapping.save_map` (`data.js`, `lines.js`), the list in `runs.write_index` (`runs.js`) and their types in `viewer/src/types.ts`.
- `params.py` help texts and the options table in README.md describe the same options. The web form is generated from `SearchParams` too (`web.schema`): a new field that takes a file path or a secret must be `cli_only`, or the web would accept it. `web_only` fields (`geometry`, a drawn area checked by `area.check_geometry`) are set by the server, left out of the form, argparse and README.
- `settings.Limits` (fields, `PUBLIC`, `BOUNDS`), the table "Limits of the web app" in README.md and the form: `web.schema(limits)` gives the form `min`/`max` and leaves out what `not_allowed` forbids, `search/SearchPanel.tsx` puts them on its inputs (`Setting`, the ranges of radius, buffer and the key fields). A new limit on a request value is a field plus an entry in `BOUNDS` (or its own check in `check_request`) and a README row; a new quota or rate is a field, a `PUBLIC` default, its check (`Jobs.admission`, `Jobs.use`, `web.within_rate`) and a README row.
- The tiers of the accounts: `accounts.User.limited` (not an administrator, not `users.unlimited`) decides in one place; `web.user_limits` (request values and the form), `jobs.unlimited` / `quick.unlimited` (the worker's search limits and quotas: `run_phase`, `run_quick`), `Jobs.admission(limited=)` and `web.within_rate` follow it. The safeguards (`queue_max`, `free_disk_gb_min`, time limits) never depend on it. Locally the one user is `LOCAL` and `FINDALINE_LIMIT_*` apply as before (`web.unlimited` is False without `--public`).
- Tiled areas (`search.search_lines`): a line belongs to the tile whose core holds its first anchor (smaller x, then y); the overlap is `--max-length` + `search._margin` (max of `--prominence-span` and `--drop-radius`, what `terrain.py` looks at around an anchor) + 2 pixels so slopes at the edge and the anchor values match one grid; every search grid also reaches `_margin` beyond its area (not `profile_of_line`: `with_margin=False`). The pair search of a tile starts only from the anchors in its core and takes partners after them in that order (`find_valid_lines(first=...)`, `_pairs` with `first_only`), the same rule as the filter in `search._lines`. The web worker keeps the tile size of the download phase (`tile_core.json` in the job folder), so both phases announce the same tiles. R14 and `tests/test_offline.py::test_area_in_tiles` check that tiles give exactly the lines of one grid (inland, no water: water and gap filling work per tile and may differ at tile borders).
- `helpers.max_safe_elevation` defines the clearance limit; `evaluate_line` and `line_profile` use it. `linesearch._line_ok` repeats it in numba (formula and sag table) and `find_valid_lines` derives the weakest per-anchor limit from it (`gain`, `cap`, `offset`): change all three together. All three sample the pixels between the anchors as `r1 + rint(dr * t)` (the offset is rounded, not the position: `rint` rounds halves to even, which would make results depend on where the grid starts). The kernels may only pass too much, never too little (EPS); `evaluate_line` makes the final decision, so results equal the plain pixel-by-pixel search. That decision runs as `linesearch._evaluate` (numba, parallel), a copy of `evaluate_line` with the same arithmetic (`_interp` repeats `np.interp` to the last bit): `tests/test_units.py::test_evaluate_lines_matches_evaluate_line` compares them with `==`. The regression set compares the sha256 of `lines.csv` too (with totals: length, clearances), so such a change must leave every checksum as it was.
- Heights of the webbing above the terrain (`height_max`, `height_mean`, `high_pct` of `--high-above`) are the margin below `max_safe_elevation` plus `helpers.fall_allowance` (leash fall or fall zone): `helpers.webbing_height`, repeated in `_evaluate` and used by `line_profile` (`max_height`). The mean is summed one pixel after another in both (`np.cumsum`, not `np.mean` or `sum()`, which is compensated since Python 3.12). A change of `max_safe_elevation` changes the heights too.
- Wall angles: `helpers.downslope` (Horn 3 × 3 at each anchor) and `helpers.wall_angles` give the saved angles and the final decision of `--max-wall-angle` (`LineLimits`, in `evaluate_lines`); `_pairs` drops pairs earlier with the cosine of the limit, within EPS, so it may pass too many, never too few.
- `web.RUN_FILES` (the files of a run the public site serves) and what `mapping.save_map` and `runs.save_results` write (`map.html`, `data.js`, `lines.js`, `lines.csv`, `lines.geojson`, `ATTRIBUTION.txt`): a new file a map needs goes into both, a file with the owner's details (`run.json`) or work state (`progress.json`, `tiles/`) into neither. `window.FINDALINE_APP` (`profiles`: may the map compute profiles and measure; `favourites`: may it mark favourite lines) is written by the dynamic `runs.js` of `web.py` and read by `viewer/src/main.tsx` (declared in `types.ts`); undefined means as before (from a server yes, from disk no).
- The privacy page (`web.privacy_page`) states what is stored and for how long: `accounts.SESSION_DAYS`/`IDLE_DAYS`/`OAUTH_SECONDS`, `Limits.keep_events_days`, `jobs.DAY` (usage), `audit.KEEP_DAYS`, no IP addresses; a new stored field, cookie or retention changes it too. Every state-changing endpoint of the public site records an `audit` event (`web.record`), refusals by a quota or rate too (`queue`, `within_rate`, `Jobs.use`). The about page is built from `sources.SOURCES` credits (and their layers'), so a new source needs no change there.
- A row of `data.js` ends with the profile (`row[-1]`); new columns go before it (`toLine` in `types.ts`).
- Favourite lines are known by the anchors of their rows in `data.js`/`lines.js` joined (`keys.lineCoords`, also the `#line=` of a map's link): a change of how `mapping.save_map` rounds the anchors loses everyone's favourites (decide their migration). Their values, `web.FavouriteLine`, are the fields of `Line` in `types.ts` (`favourites.favouriteData` / `favouriteLine`): a new field of `Line` that the app's tab should show goes into all three. The rules of folders (not into themselves or their own folders, `FOLDER_DEPTH_MAX`) are `jobs.Jobs.change_folder`/`add_folder` and `folders.FolderTree` (`canMove`, `canAdd`, `FOLDER_DEPTH_MAX`): change both.

## Pitfalls learned the hard way
- **numba** compiles `linesearch.py` on the first run (a few seconds, cached in `__pycache__`). Inside `@njit` code only numpy/math and module constants work; keep the float operations in `_line_ok` in the same order as `max_safe_elevation`.
- **The viewer** works from `file://`: no `fetch`, so a run's data is a script (`data.js`) and the list of runs too (`runs.js`); everything it needs (Leaflet, its CSS and marker images) is in the bundle, no CDN. The app serves it with `style-src 'self'`: no `style=` attributes or `<style>` in HTML strings (classes, or the CSSOM: `element.style`, Preact's `style` prop); `tests/test_web.py` counts CSP violations in headless Edge. After changing `viewer/src`: `cd viewer; npm install` (once), `npm run check` (types), `npm run build`, and commit `dist/`. Users need no Node.
- **Pipes and heredocs**: piping the script's output into `head` kills it before the map is saved. Complex multi-line edits are safer as a Python script written to the scratchpad than as a bash heredoc.
- **geoportal.gov.pl data comes from sheet files**, not WCS (`SheetTiles`): the EVRF2007 WCS takes 30–50 s per ASCII tile (generating the text, not downsampling, is the cost), its own downsampling leaves holes at coarse resolutions (Tatras at 5 m), its GeoTIFF output is an 8-bit picture, and the KRON86 coverages stop at 2019. Index answers are cached per 0.25° tile in `cache/poland/sheet-index/`. The sheet files on opendata.geoportal.gov.pl download at ~17 MB/s; the geoportal pages give no request limits (technical contact service.desk@gugik.gov.pl). Sheet attributes and coverage are in docs/roadmap.md ("To check").
- **Half-pixel grid alignment**: data whose pixel centres lie on whole metres (geoportal sheets: `xllcenter`) must get `grid_origin=0.5`, otherwise the mosaic interpolates it bilinearly half a pixel off and smooths cliff edges (R2 at 1 m lost 40% of its lines). Comparing rasters from two services needs the same care.
- **Telling surveys apart**: two services resample differently, so compare their difference with the difference of the candidate source files (difference of differences); a residual around 0 shows which survey each serves (used for KRON86 vs EVRF2007).
- **WCS services differ**: axis labels (`x/y` vs `E/N`), multipart responses (coverage part may be `image/*` or `application/*`), formats (some GeoTIFFs are whole metres; ASCII grids keep centimetres), server limits (~2000×2000 px), interpolation support. Malta's WCS answers 404 to a request that reaches beyond the coverage, which once made the whole north coast of Gozo "missing": `WcsTiles` clips such a request to the DescribeCoverage extent. A `missing` tile at the edge of a country's data deserves suspicion.
- **New sources**: research and choose the access method with [docs/data-sources.md](docs/data-sources.md) (what to find out, files vs WCS vs own hosting, quick tests); the researched countries are in the roadmap, "New data sources".
- **Our own Slovak tiles** come from the local mirror (`FINDALINE_MIRROR`, the folder above `slovakia/`) until they are on Hugging Face (`sources.SLOVAK_TILES`); without it `--source auto` falls back to `europe` and the Slovak regression test is skipped. `tools/sk_tiles.py extract` unpacks the TIFF first (GDAL's `/vsizip/` reads it about 60 times slower than Python's `zipfile` inflates it); `cut` reads full-width 2 km bands (several GB of RAM) and writes tiles on all cores: one cut at a time.
- **USGS 3DEP (the USA)**: the 1 m DEM is published per project in 10 km files of 10–450 MB, and a newer project often covers only part of a tile (Yosemite x26y418: a 10 MB sliver of 2020 over the whole tile of 2019), so "newest file per tile" loses data: `TnmBlocks` composes each block newest first and reads an older file only while holes remain; the key in a block's name stands for its set of files (a new project changes it). All 3DEP files are tiled, so GDAL `/vsicurl/` reads windows (`_gdal_http` sets our User-Agent); never download a whole file. Old 1 m names have no zone (`USGS_one_meter_x..y..`, `USGS_1m_x..`): `_utm_zone_of`. Alaska's IfSAR files name only the GRS80 ellipsoid of Alaska Albers (`_same_crs` takes it as EPSG:3338); there is no 1 m DEM in Alaska (2026-10), so `alaska` switches to `alaska_ifsar` (`Source.instead_without_data`). Texts printed to the console stay in cp1250 (a Windows console): "1/3 arc-second", not ″, in names, descriptions and notes.
- **Check georeferencing of every new source** against Copernicus DEM (shift search, see regression doc). Malta 2012 is off by (-56 m E, -196 m N), corrected by `MALTA_2012_SHIFT`.
- **Water/gap filling order**: sea zone first, then gaps on land outside it, then water. Gap offsets are matched on gentle slopes only and limited to ±3 m from the overall offset; no anchors at gap seams. Cliffs can be vertical: high land next to water is normal.
- **geoportal orthophoto**: `ORTO/WMS/HighResolution` holds only sheets of 10 cm or finer (mostly towns) and answers elsewhere with a white JPEG (667 bytes), not an error; the gaps come from the base tiles (`OrthoService.base_url`: the `ORTO/WMTS/StandardResolution` GetTile in EPSG:3857, zoom 0–19). The `ORTO/WMS/StandardResolution` answers about half of the requests with 404, and its session cookie keeps a browser on the failing server: not used. A tile with white 8×8 blocks is on the edge of the coverage and is composed from the transparent PNG of the WMS over the base (`orthophoto.tile_content`).
- **Public services are flaky**: Overpass is often overloaded and slow (30–70 s per 0.25° theme tile; the world file in `cache/osm/water-polygons/` is used instead when present; inland areas skip the coastline); the OpenTopography demo key `demoapikeyot2022` has a shared limit of 50 calls/day; Nominatim allows 1 request/s. Both limits hold across all processes of a data folder (CLI, web, worker, phase processes): Nominatim requests go through `osm._ask` (a pyrate-limiter `SQLiteBucket` in `cache/osm/nominatim-rate.sqlite`, one per 1.1 s; cached answers never touch it), Overpass queries through `osm._overpass_turn` (`filelock` on `cache/osm/overpass.lock`, one at a time, `requests.Timeout` after 10 min); never call either service around them. A user's quota of uncached Nominatim requests is `osm.BEFORE_REQUEST`, set by the web worker per job or quick task (`jobs.nominatim_quota`); it raises `jobs.QuotaExceeded` (a `ValueError`, so an optional lookup such as a run's place name goes on without it) before the request. Every request sends `cache.http_headers()` (one User-Agent; the operator's contact from `FINDALINE_CONTACT` on a public site). Failed Nominatim lookups are asked again after 30 days; outlines above 5 MB are stored simplified.
- **Named areas are land**: Nominatim's `osm:Gozo` is the island only (no islets, no sea). `--within osm:<name>` therefore selects the coastline/cliffs within `--max-length` of it (`area._near`) instead of clipping to it.
- Grid snapping and the circle mask make results sensitive to the exact centre: a centre 0.4 m away changes a few lines at the edge.
- **Updates** (`update.py`): a dataset that can change needs a TTL (`cache.TTL_DAYS`, `Layer.ttl_days` from `/live` in the folder) and a way back from its path to its tile (`Layer.tile_of`), otherwise `cache update` skips it. `osm.THEME_TAGS` defines a theme for both Overpass and the extracts: a new theme is one entry there, and the extracts must be taken again (`osm update` or a new download).
- **pyosmium**: the extracts are read in three filtered passes (tagged objects, ways of relations, nodes by id) instead of `with_locations()`, whose node index for Poland would take gigabytes; Poland (2.1 GB) takes about 10 s. A theme tile comes from the extracts when the part outside their outlines lies in no other country of the Geofabrik index (open sea); a coastal tile is rarely covered whole by a country's outline. Overpass has a second server (maps.mail.ru; overpass.osm.ch holds Switzerland only). Geofabrik keeps dated extracts (`<region>-YYMMDD.osm.pbf`), handy for testing the diffs. The OSM world water polygons are regenerated daily, so they are only checked after a year (a check means a 900 MB download).
- **viewer/dist is committed**: the global `dist/` rule of `.gitignore` has an exception (`!viewer/dist/`), and `.gitattributes` marks it `-text`, so git never changes its line endings (the test compares it byte for byte with a fresh build). Start scripts keep their line endings (`*.sh`/`*.command` LF, `*.bat` CRLF).
- **Every endpoint checks who asks, through its dependencies**: `current_user` (signed in and approved; locally `accounts.LOCAL`, an administrator), `require_admin`, `run_access`, and those built on them (`visible_job`: own jobs, an administrator's all; `own_job`: edit and run again, own only). Never an ad-hoc check inside the endpoint: `tests/test_public.py::test_every_route_has_its_access_rule` fails for a route outside `web.PUBLIC_ROUTES` without one. Another user's job or run answers 404, not 403. Jobs carry `user_id` (NULL: the local app's or from before the accounts); the event stream filters by it (`Jobs.events(user_id=...)`), at most `SSE_PER_USER` streams per user; `_search_hash` includes the owner (`Plan.owner`; None locally, so the hash of before).
- **Run folders are never served statically on the public site**: `/runs` is `web.RunFiles` (a `StaticFiles` subclass: only `RUN_FILES` of a run the request's user may open, `_viewer/` for anyone, served from the code's `viewer/dist`, never from `runs/_viewer`, which the worker writes; 404 for everything else, an empty path part too; Starlette's path checks, ETag and Range); `/runs/runs.js` is generated per user (own runs) and `/runs/index.html` redirects to the app. The owners are the table `runs` of `jobs.sqlite` (the worker adds the row when a job saves its run; at the start of `web --public`, `Jobs.adopt_runs` gives runs without a row or owner to the first administrator of `FINDALINE_ADMINS`, whose user row is made then if needed). Locally `/runs` is the plain folder as before (tests put their test pages there). Share links: `/s/<token>/<file>` is another `RunFiles` (the run found by the sha256 of the token, `Jobs.shared_run`; none once its owner is blocked), `/s/_viewer/` the viewer, `/s/runs.js` sets only `FINDALINE_APP = {profiles: false}` (no `FINDALINE_RUNS`: the map shows its own run only), `/s/index.html` redirects to `/`; the map's `../../cache/...` lands on `/cache/` (orthophoto tiles, open to anyone). The owner makes, renews (`POST /api/runs/<id>/share`, the link is shown once) and revokes (`DELETE`) the link; a share page must never reach another run.
- **Sign-in** (`accounts.py`): Authlib keeps state, nonce and PKCE verifier in `request.session`, the signed cookie `__Host-findaline-oauth` of Starlette's `SessionMiddleware` (10 min); never configure Authlib's cache (it moves the state out of the browser's cookie). The callback address comes from `FINDALINE_PUBLIC_URL`, `next` only through `accounts.local_path`. Our session cookie `__Host-findaline` holds a token whose sha256 is the row in `sessions`; the CSRF token of the page is the session's, compared with `secrets.compare_digest`. Errors of the ID token's checks are `joserfc` errors (`JoseError`), not `OAuthError`. `__Host-` cookies need `Secure`: tests use an `https://` `base_url`.
- **The web worker** runs each phase in a `spawn` process; its stdout becomes `info` events, and `progress.TEXT_INTERVAL` is set to infinity there (progress goes as events). The worker may be another process than the web server (`web --no-worker` + `worker`, the public setup): the two talk only through `jobs.sqlite` (claims, `cancel_requested`, the `workers` leases), never through memory. Only jobs of a worker whose lease expired (`LEASE`, renewed every `HEARTBEAT`) are failed as interrupted, so restarting `web` never touches a running job; a phase ends a job only if it is still in that phase's status (`Jobs.set(..., when=...)`), so a cancelled or failed job stays so. The web process does no search work: estimates and profiles are rows of the table `quick`, which one process of the worker answers one after another (so `search`/`sources` state is never shared between threads); the endpoint waits with `asyncio.sleep`, and answers 503 without a worker. A tiled area stopped by cancelling or closing the app resumes on the next start of the same search. On the public site every text that reaches the page goes through `Jobs(public=True)` (`event`, `set(error=...)`, `quick_answer`): write new messages through these, never around them. The page is drawn again on every queue event: form fields must not take their value from state that changes only on `change` (text fields: `onInput`; number fields: `defaultValue`), or typing is reset.
- **Limits are checked on validated values**: `web.checked_request` validates the request (`SearchParams`) and `Limits.check_params` compares what pydantic read ("5_e3" is 5000 there, and `float()` refuses it), never the raw JSON; the worker repeats the bounds (`search._check_params` in `plan_search`). A bound that needs the resolution takes the parsed one.
- **Heavy work and network only in the worker**: the web process validates and queues; estimates and profiles go to the quick lane; it never imports `search` or `numba` (`tests/test_public.py` checks it), so it needs no numba cache. A check that can refuse cheaply (rates, quotas: `Jobs.precheck`) comes before validating a request.
- **Every waiting loop has a deadline**: `web.quick` waits at most `QUICK_WAIT_MAX` (the lane's time limit per task ahead) and stops when the client goes away (a task awaiting `http.disconnect`: `Request.is_disconnected` never sees it behind the `guard` middleware, a `BaseHTTPMiddleware`); an event stream re-checks its session every `SESSION_CHECK` seconds; the worker's phases and the quick lane have time limits on the public site (`PUBLIC`). A new loop that waits for another process or a client needs the same.
- **Search limits** (`Limits`, the worker's) must refuse before the cost they guard: the bounding box (`bbox_km_max`) of the area before the source is chosen and before any index, Overpass or data request, then of the grid; the region size in `area.region` comes before `osm.theme`, the pixel and tile checks before `_tiles` and `layer.estimate`, the line limit before the profiles. They only refuse (or make tiles smaller to fit `grid_mpx_max`): with `limits=None` (CLI, regression) nothing changes. The worker passes its `Limits` to its spawned processes as an argument; `jobs.ortho_confirm` sets `search.CONFIRM_MINUTES` there (as `pg.TEXT_INTERVAL`).
- **Shell on this PC**: `cat > file` without a here-document waits for input forever; nested quotes in `python - <<EOF` scripts break easily (write the script with the Write tool instead). Stop only test browsers: filter `msedge.exe` by the `--user-data-dir` of the test (PowerShell `Get-CimInstance Win32_Process`), never all Edge processes of the user.

## Verifying changes
- Follow [docs/regression-tests.md](docs/regression-tests.md): run the affected locations and compare with the expected numbers.
- Map/JS changes: `tests/test_viewer.py`, then generate a small map (the Żabi Koń clip in `tests/data`, offline), append a test `<script>` to a copy and run headless Edge (`msedge --headless --dump-dom` for checks, `--screenshot` for a look; `window.FINDALINE_MAP` is the Leaflet map; in the app page `window.FINDALINE_PLACE` is its `PlaceMap`, and `tests/test_web.py` has `_edge_page` with stubs for the event stream). Synthetic `mousemove` works; headless screenshots don't keep hover state. "Other runs" across coordinate systems: reproject the clip to UTM (rasterio) and run it as a second run.
- Cache update code: a scratch `--data-dir`, `checked_at` aged by hand in its `index.sqlite`, then `cache status` / `cache update` (see the regression doc).
- New download code: test on an empty cache (`tests/regression.py --cache <temp>/cache`, or a scratch `--data-dir`), so the real cache is not touched.
- New data source or download path: also check the share of valid pixels at the coarsest resolution (5 m) and compare a few tiles with the source files (see the regression doc, "Data checks for a new source").
- The Polish set (R13, R1–R5) takes about 3 min with an empty geoportal cache; run the tests one after another, never two searches at once.

## Conventions
- Code, comments, docs and commit messages in English; conversation with the user in Polish.
- Match the existing style (docstrings, comment density). Commit messages end with the `Co-Authored-By` line.
- One branch per task, started from the current `main` and named after it (e.g. `cliff-angles`, `source-austria`); never commit to `main` directly. Parallel agents each work in their own worktree (`.claude/worktrees/<task>`, `git worktree add`), so they never share a checkout. A finished task is merged into `main` (rebase onto `main` first if it moved), then its branch and worktree are deleted. Nothing is pushed unless the user asks.
- Parallel tasks share the data folder and the cores: downloads may overlap, but `pytest` and `tests/regression.py` of two tasks must not run at the same time (the regression numbers assume one search at a time). Two tasks touching the same "Things that must stay in sync" pair will conflict: split such work differently.
- Generated data (`cache/`, `runs/`, `work/`, `jobs.sqlite`, `findaline_map.html`) is git-ignored. The app has many potential users (the public site of stage 4): for every change of stored data (cache layout, runs, SQLite databases) decide explicitly whether it gets an automatic migration (SQLite schema versions with `PRAGMA user_version`) or none, and state the decision in the commit message.
- Libraries first: before writing an own implementation, look for a popular, maintained library (current version, release cadence, known CVEs) and present a comparison to the user, who decides. Own code stays only where libraries fit worse, with the reason recorded (docs/roadmap.md, "Stage 4").
